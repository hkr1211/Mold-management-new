# 模具管理系统评估报告（基于当前代码库）

> 评估时间：2026-04-30（UTC）
> 评估范围：`app/main.py`、`app/pages/*.py`、`app/utils/*.py`、`alembic/*`、`sql*`、`docker-compose.yml`

## 结论先行

- **问题1（落地实施）**：系统具备可演示的业务闭环雏形（模具、借用、维修、部件、排程、成本等页面），但“上线可运营”层面仍不完善，尤其是**功能完成度不均、数据模型一致性、权限与审计、测试与运维**。  
- **问题2（系统架构）**：当前“Streamlit 单体 + PostgreSQL”路线适合中小团队快速落地，但代码呈现出**分层不清、命名与schema历史包袱、迁移通道分散**等问题，架构合理性“中等”，完善度“偏低”。

---

## 1）从落地实施角度看：功能设计是否完善？

### 1.1 已有能力（可落地的基础）

1. 入口具备登录、会话状态、页面导航与多模块入口。  
2. 页面模块覆盖了典型模具管理域：模具、借用、维修、部件、系统管理、推荐、成本、排程。  
3. 借用与维修页面里已实现较多业务细节（搜索、状态判断、预警、表单化流程）。

### 1.2 不完善点（会影响真实上线）

#### A. 模块完成度不均衡（“能看”不等于“能用”）
- 模具管理页含大量调试输出，且“新增模具”仍是“待实现”占位文本，这意味着核心主数据维护功能未闭环。  
- 这类页面直接影响首批上线用户（库管/工程师）日常录入和数据可信度。

#### B. 权限设计存在“设计意图”和“实际调用”错位
- 权限字典是硬编码的；部分页面检查的权限名（如 `create_mold`）在权限映射里并不明显匹配，存在“有角色但无权限点定义”的风险。  
- 对企业场景而言，权限应可配置，不应每次组织变更都改代码。

#### C. 数据模型与SQL存在不一致风险
- 模型层 `SystemLog` 使用 `user_id_fk/created_at` 命名，而认证日志 SQL 使用 `user_id/timestamp` 写入语句，实际运行时容易因为字段不一致而失败。  
- 同仓库中同时出现多套 SQL 初始化/修复脚本，也提示 schema 演进路径并不唯一。

#### D. 业务流程“状态机化”不足
- 借用、归还、审批、维修、保养、寿命冲次等流程跨表联动较多，当前主要靠页面逻辑与 SQL 拼接推进，缺少统一领域状态机与事务边界定义。  
- 并发用户增加后，容易出现状态覆盖、重复提交、审批穿透等问题。

#### E. 上线运维要素缺口
- 缺少明确的健康检查、失败重试规范、慢查询治理、告警阈值和恢复演练流程文档。  
- 当前更偏“开发调试态”，还不是“生产运营态”。

### 1.3 落地评分（建议）

- 功能覆盖广度：**8/10**（模块多）
- 功能完成深度：**5/10**（关键模块未闭环、调试痕迹重）
- 一致性与可运营性：**4/10**（schema/权限/审计风险）
- 综合落地成熟度：**5.5/10**（建议先做稳定化再推广）

## 2）从系统架构角度看：是否合理和完善？

### 2.1 合理的部分

1. **技术选型合理（阶段性）**：Streamlit + PostgreSQL + Docker/Nginx 对“内部业务系统快速上线”是合理组合。  
2. **数据库基础能力可用**：有连接池与统一查询入口。  
3. **已具备迁移框架**：仓库中存在 Alembic 结构，说明团队有版本化迁移意识。

### 2.2 不完善/不合理的部分

#### A. 分层不清（UI/业务/数据访问耦合）
- 页面层直接承载大量 SQL 与流程判断，导致“改一个流程影响多个页面函数”，测试成本高。

#### B. 数据访问模式混杂
- ORM 模型、原生 SQL、修复脚本并存；字段命名风格混用（`*_fk` vs 非 `*_fk`），加大维护复杂度。

#### C. 迁移治理不收敛
- Alembic 与多个 SQL 修复脚本并行，容易形成“线上库状态不可预期”的治理风险。

#### D. 安全与审计链路不够稳
- 虽有密码哈希与登录尝试限制，但权限仍硬编码，日志字段不一致风险会直接影响审计闭环。

### 2.3 架构成熟度判断

- 架构方向：**合理（适合当前规模）**
- 架构落地质量：**中等偏下**
- 主要问题不是“选型错”，而是“工程化收敛不足”

---

## 3）建议（简版）

虽然你这次只问了前两点，但为了让评估可执行，给一个最短落地建议：

1. **先统一 schema 真相源**：Alembic 成为唯一 DDL 通道，清理散落修复脚本。  
2. **补齐主数据闭环**：优先完成“新增/编辑模具”与字段校验。  
3. **权限表驱动**：从硬编码角色权限迁移到 `roles/permissions/role_permissions`。  
4. **抽 Service 层**：把借用/维修跨表流程从页面中抽出，统一事务管理。  
5. **最小自动化回归**：登录、借用申请、审批、归还、维修工单、日志写入 6 条主链路。
